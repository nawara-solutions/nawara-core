## 1. Responsibility

**Owns:** the file object (`fileId` → immutable bytes), its generic metadata, integrity (SHA-256), lifecycle (upload, availability,
expiry of unattached files, deletion), the storage port and its adapters, safe byte serving, and the authorization boundary for
bytes (which caller may act on which file).

**Does not own:** business meaning (document type, student, contract, invoice), business relationships (`StudentDocument.fileId`
lives in Drive), document versions, user identity or membership, entitlement or quotas from Billing, audit history (Stage 18),
message delivery (Notification). It never calls a product service, and never learns a product's model.

## 2. Consumers (validation of the abstraction; none implemented here)

| Consumer | Use | Path | Notes |
|---|---|---|---|
| Nawara Drive | student / instructor / school documents, contracts, exam evidence, photos | Drive authorizes the user, issues an upload ticket, the app uploads to File Service; Drive attaches the `fileId` to its record; downloads through download tickets | typical sizes 0.1–10 MB (phone photos, scanned PDFs) |
| Billing (future, SDD §36.5) | rendered invoice PDFs, template logo assets | service upload of generated bytes; service read for delivery | immutable; Billing keeps the content hash and `fileId` |
| Notification (deferred, ADR-0046 §16) | email attachments by `fileId` | service read at send time (delegated by the file's owner) | size and type bounded for email |
| Security / Admin (Stage 19, future) | controlled exports | service upload; short-lived download | sensitive |

Everything above is documents and images, measured in megabytes. No consumer needs large media, resumable or multi-gigabyte
transfer in V1; that shapes F8 / F9 / F29.

## 3. Data model (conceptual; tables are Stage 17.3)

**`file`** — one row per file, never hard-deleted (a tombstone remains after the bytes are gone).

| Field | Source | Mutability | Exposed | Notes |
|---|---|---|---|---|
| `id` | server (UUID v4, the Core convention) | immutable | yes | opaque; not authorization |
| `ownerService` | server (service token caller) | immutable | yes | the only caller with default rights |
| `organizationId` | caller (policy `none` / `request`) | immutable | yes | null = platform file |
| `createdBy` | caller (opaque actor reference, ≤ 128) | immutable | no (audit) | never verified by File Service |
| `originalName` | caller (sanitized, §8) | immutable | yes | presentation only; never a path |
| `mediaType` | **server** (verified from the bytes, §7) | immutable | yes | the declared type is only a hint |
| `declaredMediaType` | caller | immutable | no | kept for diagnosis of mismatches |
| `sizeBytes` | server (counted) | set once | yes | |
| `sha256` | server (computed while streaming) | set once | yes | integrity, not authorization |
| `storageProvider`, `storageKey` | server | immutable | **never** | opaque key, §6 |
| `status` | server | state machine §5 | yes | |
| `attachedAt` / `attachDeadline` | server | set once | yes | unattached = temporary, §5.2 |
| `idempotencyKey`, `requestHash` | caller / server (keyed HMAC) | immutable | no | §10 |
| `createdAt`, `availableAt`, `deletionRequestedAt`, `deletedAt` | server | set once | yes (not `deletedAt` detail) | |
| `failureCode` | server | set once | yes | bounded machine code |

**`file_access_ticket`** (§11.1): `id`, `operation` (`download` | `upload`), `fileId` (download) or the upload intent (upload:
`organizationId`, `maxBytes`, allowed media types, attach-on-completion flag, then the created `fileId`), `issuedBy` (the owner
service), `organizationId`, `tokenDigest` (SHA-256 of a random 32-byte token; the token itself is never stored), `expiresAt`,
`singleUse`, `usedAt` / `useCount`, and for downloads the requested disposition. **`file_delegation`** (Notification attachments, later): owner-issued read grant
`fileId` → grantee service, until a time.

No business reference table exists (F4).

**Implemented (Stage 17.3, `0001_file_schema.sql`); clarifications the implementation settled, no decision changed:**
- `mediaType` is **set once when known**: NULL while `UPLOADING` (the type comes from the bytes, 17.5), required from `VERIFYING` on,
  like `sizeBytes` and `sha256`. `originalName`, `createdBy` and `declaredMediaType` are optional.
- The lease `uploadExpiresAt` (§5.1) and `updatedAt` are columns; digests (`sha256`, `requestHash`, `tokenDigest`) are lowercase hex.
- The ticket carries `revokedAt` (revocation, §11.1); `usedAt` is the **first** use and `useCount` counts every use.
- The Idempotency-Key is unique per owner among **live** files only: a `FAILED` / `REJECTED` attempt frees it for the retry of §10.
- A file row is never deleted; ticket rows may be (retention).

## 4. Storage port (Stage 17.4)

```ts
interface StoragePort {
  put(key: StorageKey, body: Readable, opts: { sizeBytes: number; contentType: string; sha256?: string; signal: AbortSignal }): Promise<void>;
  get(key: StorageKey, opts: { signal: AbortSignal }): Promise<Readable>;        // a stream, never a buffer
  head(key: StorageKey, opts: { signal: AbortSignal }): Promise<{ sizeBytes: number } | undefined>;
  delete(key: StorageKey, opts: { signal: AbortSignal }): Promise<void>;         // idempotent: a missing key is success
}
```

Errors are normalized to `storage_unavailable` (retryable), `storage_timeout` (outcome unknown for `put`), `storage_not_found`,
`storage_rejected` (configuration or permission: operator fault), never an SDK class. Adapters: `S3CompatibleStorage` (production;
the SDK or a signed-HTTP client is chosen in 17.4 under the same no-unbounded-timeout rule as 16.8) and `FilesystemStorage`
(development and tests: a configured root, keys validated against the key grammar, no path from user input, refused in production).
Adapter tests run against MinIO in a container.

**Implemented (Stage 17.4); clarifications, no decision changed:** the adapters are `FilesystemStorage` and `S3Storage` (provider
names `filesystem` / `s3`, recorded in `file.storageProvider`); `get` returns `{ body, sizeBytes }`; `put` never replaces an object
(`If-None-Match: *` / `link`) and enforces `sizeBytes` and an optional `sha256` before publishing; the error set adds
`storage_already_exists`, `storage_invalid_key`, `storage_length_mismatch`, `storage_checksum_mismatch`. The S3 adapter tests run
against an S3-protocol test server (VersityGW in CI and the `storage-test` Compose profile), because MinIO no longer publishes public
container images; the test server is infrastructure, never a provider choice. The S3 compatibility checklist is in the 17.4 record §12.

## 5. Lifecycle

### 5.1 States

```text
 service upload / ticket upload
            │
            ▼
        UPLOADING ──(stream error, client abort, storage failure, timeout)──► FAILED
            │  size / type / checksum refused ───────────────────────────────► REJECTED
            ▼
        VERIFYING  (only when a scanner is configured, F19; otherwise skipped)
            │  scanner verdict: infected ──────────────────────────────────────► REJECTED (quarantined)
            ▼
        AVAILABLE ──(delete, expiry of an unattached file)──► DELETING ──(bytes gone)──► DELETED
```

- `UPLOADING` carries a lease (`uploadExpiresAt`): a crashed upload is recovered as `FAILED` by a sweep, and its partial object is
  deleted.
- `REJECTED`, `FAILED` and `DELETED` are terminal; their bytes are removed (a `REJECTED` infected file is kept in a quarantine prefix
  only if the malware policy asks for it).
- Downloads are served only from `AVAILABLE`.

### 5.2 Temporary and attached

A new file is **temporary** (`attachedAt` null, `attachDeadline` = created + `FILE_ATTACH_TTL`, default 24 h). The owner calls
**attach** once its own business record holds the `fileId`; attach is idempotent. An unattached file past its deadline is deleted by
the cleanup worker (orphan protection, F18). Generated files a service uploads for itself can be created attached.

### 5.3 Crash windows (database and storage never share a transaction)

| Window | State left | Recovery |
|---|---|---|
| row `UPLOADING` committed, storage write fails | `UPLOADING` | the upload returns an error and marks `FAILED`; if the process died, the lease sweep marks `FAILED` and deletes any partial key |
| storage write succeeds, `AVAILABLE` update fails | `UPLOADING`, object present | lease sweep → `FAILED` + delete the object (the client retries with the same `Idempotency-Key` → a clean retry) |
| `AVAILABLE`, object missing (operator error, provider loss) | `AVAILABLE` | a read gets `storage_not_found` → `file_content_missing` error, a `file_storage_inconsistent` signal; reconciliation reports it (§12) |
| `DELETING` committed, storage delete fails | `DELETING` | the delete worker retries with backoff (delete is idempotent) |
| storage delete succeeds, `DELETED` update fails | `DELETING`, object gone | the retry deletes a missing key (success) and marks `DELETED` |
| object with no row (a write after the row was swept) | orphan object | the key prefix is never listable by a user; reconciliation deletes orphan keys older than the lease |

## 6. Storage keys

`<prefix>/<fileId>/<random 16 bytes, hex>`: opaque, unique, server-generated, path-safe (the adapter validates
`^[a-z0-9/-]{1,200}$`). No organization, filename or type in the key (no leak through listings or logs). `fileId` ≠ storage key, and
knowing a key grants nothing: buckets are private, and no permanent public URL exists.

## 7. Content validation

- **Size:** `Content-Length` is required; the stream is cut at the effective limit (min(global ceiling, caller policy, ticket
  limit)) → `413 file_too_large`. Nothing is buffered in memory beyond a small head window.
- **Media type:** the first bytes (magic numbers) decide the type; the declared `Content-Type` and the filename extension are hints
  that must agree with it, or the upload is `415 unsupported_media_type` / `422 media_type_mismatch`. V1 allow-list (F13, owner may
  extend): `application/pdf`, `image/jpeg`, `image/png`, `image/webp`, `image/heic`, `image/heif`. Refused by default: HTML, SVG,
  scripts, executables, archives, Office formats (macro risk), unknown types. Per-caller policy may narrow the list, never widen it.
- **Checksum:** SHA-256 computed while streaming. A client may send `Content-Digest: sha-256=:…:` (RFC 9530); a mismatch is
  `422 checksum_mismatch`, and the object is deleted. The provider checksum is used by the adapter where available, as a second check.
- **Deduplication:** none (no cross-tenant content addressing; the checksum is never used to find another tenant's file).

## 8. Filenames

`originalName` is presentation metadata: NFC-normalized; C0/C1 controls, bidi overrides (U+202A–202E, U+2066–2069), path
separators and NUL removed; `..` segments meaningless (never a path); at most 255 UTF-8 bytes (truncated on a code-point boundary,
keeping the extension). Arabic, French and other Unicode names are kept. On download, the header is
`Content-Disposition: attachment; filename="<ASCII fallback>"; filename*=UTF-8''<percent-encoded>` (RFC 6266 / 8187), built by one
encoder; the raw name never reaches a header. Filenames are treated as personal data and are not logged.

## 9. Serving bytes

- Only `AVAILABLE` files; streamed (backpressure end to end; client disconnect aborts the storage read).
- Headers: `Content-Type` = the verified type; `Content-Disposition: attachment` by default (`inline` only for the image allow-list
  and only when the caller asks); `X-Content-Type-Options: nosniff`; `Content-Security-Policy: default-src 'none'; sandbox`;
  `Cache-Control: private, no-store`; `ETag` = the SHA-256 (immutable content).
- No `Range` in V1 (documents and images; F9). Ticket URLs are never logged (§15).

## 10. Idempotency

Service upload: `Idempotency-Key` (required, per caller) + a keyed request hash (HMAC-SHA-256 under a dedicated key, over the
declared metadata: organization, name, declared type, length, and the client digest when sent). Same key + same declaration →
the same file (the body is not re-stored); a different declaration → `422 idempotency_key_reused`; a key whose upload is still
`UPLOADING` → `409 upload_in_progress`; a `FAILED` / `REJECTED` attempt may be retried with the same key. Attach and delete are
idempotent by state. Upload tickets are single-use (a second redemption of a completed ticket returns the same file).

## 11. Authorization

- Every route is service-only or ticket-only; nothing trusts a caller-chosen owner (the owner is the token's caller).
- **Caller policy** (`FILE_SERVICE_POLICY`, deny by default, as Notification's): per caller, `operations` (`upload`, `read`, `attach`,
  `delete`, `issue_ticket`), `organizations` (`none` | `request`), `mediaTypes` (a subset), `maxBytes` (≤ the global ceiling).
- A caller acts only on files it owns, and must present the file's `organizationId` (or none); any mismatch is `404 file_not_found`,
  indistinguishable from a missing file (no enumeration, and a product bug that passes another tenant's `fileId` fails closed).
- **Cross-service read** (Notification attachments) only through an owner-issued delegation (§3), designed with attachments.
- **End users (F16, decided: Option C):** the product authorizes the user against its business resource, then asks File Service for
  a short-lived ticket bound to one file (or one upload) and one operation; the client redeems it directly on File Service. File
  Service never verifies user tokens and never calls Auth. **Option A** (service-token routes) stays for trusted internal services;
  **Option B** (user token + a synchronous Auth membership lookup) is rejected: membership cannot authorize a specific business
  resource, and downloads would depend on Auth.

### 11.1 Access tickets

- **Form: opaque and server-side.** A ticket is 32 random bytes (base64url) returned once to the issuing service; File Service
  stores only its SHA-256 digest (a 256-bit random value needs no key, unlike a phone number) with the bindings below. Chosen over a
  signed self-contained token because every redemption reads the file row anyway (status, organization), so a lookup by digest costs
  one indexed read, and it gives immediate revocation, true single use, no signing keys to rotate, and no state spread across
  instances (the database is shared).
- **Bindings, all checked at redemption:** the operation (a download ticket never uploads, deletes or reads metadata; an upload
  ticket creates exactly one file within its limits and never touches an existing one); the file (download) or the upload intent;
  the issuing owner service (it must still be the owner and still hold `issue_ticket` in its policy); the organization (copied from
  the file, re-checked against it); the expiry; the file status (`AVAILABLE` for a download).
- **Lifetime:** short, within 60–300 s (the default is frozen in 17.6); never extended.
- **Use:** upload tickets are single-use (a conditional update claims them; a retry after completion returns the created file);
  download tickets are reusable until expiry by default (mobile retries, a browser's second request) and may be issued single-use.
- **Revocation:** deleting the file, or revoking a ticket (owner route), invalidates it at once; expired rows are removed by the
  retention worker.
- **Leakage:** the token travels only in the redemption URL path; File Service never logs ticket paths or tokens (request logging
  redacts `/file/t/*`), sends `Referrer-Policy: no-referrer` and `Cache-Control: no-store`; a leaked ticket grants one operation on
  one file until its short expiry. Failed redemptions are rate-limited (F32) and all failures return the same `ticket_invalid`.
- **Not a general credential:** no ticket lists, searches, attaches, deletes or issues other tickets; there is no refresh and no
  OAuth-style flow.

## 12. Cleanup and reconciliation (Stage 17.7)

Bounded workers (`PollLoop`, `SKIP LOCKED`, the Notification 16.9 batch pattern with a materialized CTE): the upload-lease sweep
(`UPLOADING` past lease → `FAILED` + delete), orphan expiry (unattached past deadline → `DELETING`), the delete worker (`DELETING` →
storage delete → `DELETED`, retried with backoff), ticket expiry. Reconciliation (operator tool, not a continuous scanner in V1):
`AVAILABLE` rows whose object is missing, and objects older than the upload lease with no row, reported and optionally repaired.

## 13. API contract (V1, proposed; routes are fixed in 17.5 / 17.6)

Prefix `/file` (Core ADD API convention). Every route except ticket redemption requires a service token and the caller policy.

| Route | Caller | Purpose | Success |
|---|---|---|---|
| `POST /file/files` (headers `Idempotency-Key`, `Content-Length`, `Content-Type`, `X-File-Name`, optional `X-Organization-Id`, `Content-Digest`; body = the raw bytes) | service (`upload`) | streamed upload as the owner | `201 { id, status, mediaType, sizeBytes, sha256, attachDeadline }` |
| `POST /file/files/:id/attach` | owner (`attach`) | mark the file attached (idempotent) | `200` metadata |
| `GET /file/files/:id` (`X-Organization-Id` when the file has one) | owner (`read`) | metadata (never the key, provider or name encoding details) | `200` |
| `GET /file/files/:id/content` | owner (`read`) | streamed bytes with the §9 headers | `200` stream |
| `DELETE /file/files/:id` | owner (`delete`) | logical delete (idempotent) | `202` |
| `POST /file/files/:id/tickets` `{ operation: download, disposition, singleUse? }` | owner (`issue_ticket`) | short-lived download ticket | `201 { url, expiresAt }` |
| `POST /file/uploads/tickets` `{ organizationId?, maxBytes, mediaTypes, attach? }` | service (`issue_ticket`) | single-use upload intent | `201 { url, expiresAt }` |
| `DELETE /file/tickets/:ticketId` | issuer (`issue_ticket`) | revoke a ticket | `204` |
| `GET /file/t/:token` · `PUT /file/t/:token` | **ticket holder** (no identity; the ticket is the only authority) | redeem a download / upload ticket | stream / `201` metadata |

Consumed contracts: none synchronous (no call to Auth or to product services, for any operation); storage through the `StoragePort`; events published
through the kit outbox (§17). Health: `GET /health`, `GET /ready` (root, not routed publicly).

## 14. Errors

Stable codes, never localized text as the contract: `file_not_found`, `file_not_available`, `file_too_large`,
`unsupported_media_type`, `media_type_mismatch`, `checksum_mismatch`, `upload_in_progress`, `upload_expired`, `ticket_invalid`
(expired, used or unknown: one code), `idempotency_key_reused`, `file_deleted`, `file_content_missing`, `storage_unavailable`,
`rate_limited`, plus the kit's `validation_error` and the generic 401 / 403.

## 15. Observability, logging, readiness

- **Logs:** `fileId`, `organizationId`, `ownerService`, status, media category, size, machine codes, durations. Never bytes,
  filenames, storage keys, ticket tokens, signed URLs, credentials or provider responses.
- **Signals:** `file_upload_completed / _failed / _rejected`, `file_access_denied`, `file_storage_failure`,
  `file_checksum_mismatch`, `file_storage_inconsistent`, `file_orphan_expired`, `file_delete_retry`, and a periodic
  `file_ops_snapshot` (uploading, oldest lease, temporary files past deadline, deleting backlog), as in Notification (no metrics
  platform in Core).
- **Readiness:** database + migrations. Storage is not a readiness dependency (ADR-0048 §8); `storage_unavailable` and a periodic
  storage probe signal carry its health.
- **Timeouts:** connect ≤ 2 s; an idle-stream timeout (no byte for 30 s) and a whole-transfer bound derived from size and a minimum
  throughput; retries only for `head`, `get` (before any byte is sent to the client) and `delete`; never for `put` mid-stream.

## 16. Security and privacy

Documents are sensitive by default: bytes are never inspected except for type detection and the scanner, never logged; TLS in transit;
provider-managed encryption at rest (SSE) required of the production provider; no application-level encryption in V1 (F20). The threat
model is in the Stage 17.1 record §6.

## 17. Events (future; Stage 18 consumes)

`file.uploaded`, `file.attached`, `file.deleted`, `file.rejected` through the kit outbox (ADR-0037), ids only (no filename). Access
events (`file.access_denied`, sensitive downloads) are audit-service concerns designed in Stage 18.
