# Stage 20.3: release registration and lifecycle (automation)

- **Status:** PASSED on `feat/release-registration-lifecycle` (awaiting review; not committed).
- **Base:** `main` @ `a0eeda5` (Stage 20.2 merged, PR #132; [ADR-0051](../../adr/0051-release-management-and-client-compatibility.md) Accepted).
- **Scope:** CI registration and publication with a narrow per-product service policy, idempotent on the release identity, with
  `release.registered` / `release.published` audit intent in the same transaction through the outbox.
- **Not built:**
  - withdrawal, minimum-version administration and owner authority (20.4);
  - the compatibility read (20.5);
  - hardening and certification (20.6 / 20.7).

```text
CI (service identity) ──Bearer service token──▶ ServiceTokenGuard (ADR-0033: which service)
                                               ▶ ReleasePolicyGuard (ADR-0042: this capability, for THIS product; config only)
                                               ▶ DTO whitelist (body shape)
                                               ▶ one transaction: domain change + audit intent (outbox), or nothing
                                                        └─ after COMMIT: kit relay → RabbitMQ → audit-service (asynchronous)
```

## 1. Service identity: the existing architecture, reused

Service-to-service identity in Core is the ADR-0033 opaque token plus the ADR-0042 per-target policy (decision 2: "identity token + server-side policy in each target, deny
by default"). release-service uses exactly that and nothing new.

| Question | Answer (from source) |
|---|---|
| Token format | 32 random bytes (base64url), generated by `generateServiceToken()`; the callee stores only the SHA-256 digest (`SERVICE_TOKENS=<caller>:<digest>`, at most two per caller for rotation) |
| Issuer / audience / expiry / claims | **none**: the token is opaque, not a JWT (ADR-0042 §Context: "no claims, expiry, audience or scopes"). Audience is enforced **by construction**: a token is valid only at a callee that registered its digest, so another service's credential is an unknown token here (401). Expiry and revocation are rotation: replace the digest (two slots). Signed service JWTs (ADR-0042 option A.4) remain a documented evolution, not built. |
| Subject | the configured caller name (`^[a-z][a-z0-9-]{1,62}$`), e.g. `drive-ci`. It is the audit actor. |
| Verification | the kit `ServiceTokenGuard`: `Bearer <token>` only; hash, then a constant-time compare against **every** digest (no early exit); any failure is the same generic 401 |
| Policy | `RELEASE_SERVICE_POLICY`, parsed at startup (the File / Audit / Notification pattern): `{"callers":{"<caller>":{"products":{"<product>":["release.register","release.publish"]}}}}` |
| Logging / privacy | tokens and digests are never logged; denials log `release_authorization_denied caller= capability= reason=` (bounded) |
| Correlation | the kit request context: `x-correlation-id` accepted only if it matches `^[A-Za-z0-9._:-]{8,128}$`, else the request id. It is navigation only: it reaches the outbox and the audit record, and never grants anything. |

Nothing was invented:
- no API key, shared password, HMAC header, identity header, fake or synthetic user, or admin token;
- no second authorization system. The policy class follows the existing per-service caller-policy pattern.

## 2. Authority model

**Capabilities.** They are named as ADR-0051 §8 names them, `release.register` and `release.publish`, in the organization-service dotted
style. They are the only two that exist:
- the parser refuses anything else, including `release.*`, `release.withdraw` and `admin`;
- a product key must be a registry key, so a wildcard product cannot be expressed.

**Deny by default:**
- a caller with a token and no policy entry refuses to boot;
- a policy entry with no token refuses to boot;
- every route declares its one capability, and a route that declares none is refused.

**Product scope.** The capability is held **per product**, so `register` on product A says nothing about product B. The product comes
from the route, and it is compared with the caller's configured set: it is never trusted as authority.

**Order.** Authentication comes first (401). Then the capability (403 `operation_not_allowed`: the caller holds it for no product). Then
the product (403 `product_not_allowed`). Only then is the body validated (400) and the database consulted.

**No enumeration.** Because authorization never reads the database:
- an unknown product and a forbidden existing one are byte-identical answers, apart from `requestId`. This is tested.
- a forbidden caller sending a malformed body gets the 403, never a validation hint.
- the two 403 codes reveal only the caller's own configuration.

The service re-asserts the same decision (defense in depth), so the operation cannot run for a caller without authority whatever calls
it.

### Matrix (as implemented and tested)

| Caller | Product | register | publish |
|---|---|:-:|:-:|
| CI with `register` + `publish` | its product | ✅ 201 / 200 | ✅ 200 |
| CI `register` only | its product | ✅ | ❌ 403 `operation_not_allowed` |
| CI `publish` only | its product | ❌ 403 `operation_not_allowed` | ✅ |
| CI with a correct policy | another product | ❌ 403 `product_not_allowed` | ❌ 403 `product_not_allowed` |
| CI `register` on A, nothing on B | B | ❌ 403 `product_not_allowed` | ❌ 403 `product_not_allowed` |
| human member / owner / operator session | – | ❌ 401 | ❌ 401 |
| expired human token | – | ❌ 401 | ❌ 401 |
| another service's credential | – | ❌ 401 | ❌ 401 |
| unauthenticated, or identity headers only | – | ❌ 401 | ❌ 401 |

**Human tokens.** A human bearer (owner, operator or member) cannot reach these routes. It is not a registered service-token digest, so
the token guard refuses it (401) before any claim could be read. The test forges JWTs with every broad claim a confused guard might
honour (`kind: owner`, `role: admin`, `scope: release.register release.publish`, `aud: release-service`): all 401. Owner authority
begins in 20.4, for its own operations, through Auth.

**Operators** have no Release Management authority (ADR-0051 §8).

**Identity headers** have no effect, with or without a token: `X-Service`, `X-Caller`, `X-Product`, `X-Role`, `X-Owner`,
`X-Permissions`, `X-Operator`.

### Product and component bootstrap

Neither ADR-0051 nor the roadmap creates a product-management surface, and none is added.
- **Product authority is deployment configuration.** A product exists in the registry once an operator of the deployment names it in
  `RELEASE_SERVICE_POLICY`. Its row is created (idempotently) by the first authorized registration. A product key never named in any
  policy can never be created.
- **A component is declared by its first registration.** CI registers `{product, component, kind}` together, using the Stage 20.2
  primitive `ensureComponent`, which was designed for this. The kind is then fixed: another kind later is 409 `component_kind_conflict`.
- There is **no product or component endpoint, no unauthenticated creation and no human product administration**.

A mistyped component key creates a permanent, empty component. Rows are never deleted, and no release of it exists until CI registers
one. This is accepted for V1, noted for 20.6, and is exactly what the 20.2 primitives already implied.

## 3. API

Routed under `/release`. OpenAPI is at `/release/docs`, behind basic auth, and only when `SWAGGER_PASSWORD` is set. Both routes answer
`Cache-Control: no-store`.

### `POST /release/products/{product}/components/{component}/releases`: register

- **Auth:** service token + `release.register` for `{product}`.
- **Body:** `{ kind, version, buildId?, sourceRevision?, notesRef? }`. This is exactly the Stage 20.2 identity plus the kind. Any other
  field is 400 (kit DTO whitelist): an environment, channel, artifact, signing key, organization, user, flag, maintenance setting,
  `status`, `publishedAt` or `minimumVersion`.
- **Validation:** canonical SemVer is never normalized: `v1.0.0`, `1.0.0+7`, `01.0.0`, 16-digit numbers and over 128 characters are all
  400. `buildId` is `^[!-~]{1,128}$`; `sourceRevision` is `^[0-9a-f]{7,64}$`; `notesRef` is `^[!-~]{1,512}$`.

| Outcome | Answer |
|---|---|
| New | **201**, status `registered`; `release.registered` written |
| Same identity again, in any status | **200** + `Idempotent-Replayed: true`; the stored release (its current status); nothing written |
| Same version, different `buildId` / `sourceRevision` / `notesRef` | **409** `release_conflict`; nothing overwritten |
| Existing component with another kind | **409** `component_kind_conflict` |

### `POST /release/products/{product}/components/{component}/releases/{version}/publish`: publish

- **Auth:** service token + `release.publish` for `{product}`. **No body.**

| Outcome | Answer |
|---|---|
| `registered` | **200**, → `published`, `publishedAt` set; `release.published` written |
| Already `published` | **200** + `Idempotent-Replayed: true`; the same `publishedAt`; nothing written |
| `withdrawn` | **409** `invalid_transition`: the retry rule is not a lifecycle bypass (the Stage 20.2 trigger also refuses it) |
| Unknown component or version in the authorized product | **404** `release_not_found`: one answer, and publishing never registers anything |

### Failure semantics

| Class | Status / code | Written |
|---|---|---|
| Authentication | 401 (generic, no code, nothing echoed) | nothing |
| Authorization | 403 `operation_not_allowed` / `product_not_allowed` | nothing |
| Invalid input | 400 (`validation_error`, or the kit DTO message) | nothing |
| Unknown resource (publish) | 404 `release_not_found` | nothing |
| Conflict | 409 `release_conflict` / `component_kind_conflict` / `invalid_transition` | nothing |
| Idempotent no-op | 200 + `Idempotent-Replayed: true` | nothing (no evidence) |
| Database or outbox failure | opaque 500 (kit filter; `release_automation_failed operation= caller= error=<class>` logged) | **nothing: rolled back** |
| Success | 201 (register) / 200 (publish) | the row change + its audit intent, atomically |

## 4. Idempotency, lifecycle and concurrency

**Identity.** The release identity is `(component, version)`, which is ADR-0051 §11 ("idempotent on (component, version)"). The immutable
payload is `buildId`, `sourceRevision` and `notesRef`.
- A retry compares the full identity (`sameIdentity`). An equal identity is a no-op; any difference is a conflict.
- There is no last-write-wins, and no mutation is made to make a retry succeed.
- No `Idempotency-Key` header is needed, because the natural key *is* the operation. This matches ADR-0051. The organization-service
  `Idempotency-Key` pattern serves creations whose identity is server-generated, which a release's is not.

**Lifecycle.** Publication is `UPDATE … WHERE status = 'registered'`:
- `published` is the same-state no-op;
- `withdrawn` → `published` is refused;
- the database's `release_lifecycle` trigger remains the authority.

Withdrawal is not exposed. A registered-only release still cannot be withdrawn (ADR-0051); that question is left open for 20.4.

**Concurrency** is decided by the database, never by process-local locks, so it holds across replicas:
- **Registration:** the unique `(componentId, version)` with `ON CONFLICT DO NOTHING` means exactly one transaction inserts. The others
  wait for it, then read the committed row in a new statement: equal identity is a 200 no-op, a different identity is 409.
- **Publication:** the conditional `UPDATE` means the second transaction waits for the row lock, re-checks `status`, updates nothing and
  reads `published`.
- **Evidence:** only the transaction that changed the row writes evidence.

**Tested:**
- 8 identical registrations of a *new* product, component and version: one release, one 201, seven 200s, one record;
- 8 different versions of a new component: one component, 8 releases;
- identical registrations racing conflicting ones: one identity wins, the losers get 409, nothing is overwritten;
- 8 simultaneous publications: one transition, one `publishedAt`, one record.

### Two Stage 20.2 defects found and fixed

Both are real contradictions, found by the first code that used the primitives.

1. **`notesRef` could never be stored.** 0001's `release_notes_ref_shape` spelled the rule as `^[!-~]{1,512}$`. PostgreSQL refuses a
   regular-expression repetition count above 255, and it compiles the expression when the check is first *evaluated*. So the migration
   applied cleanly, and then every non-null `notesRef` failed with "invalid regular expression". The 20.2 suites only tested refusals.
   - **Fix:** migration `0002_release_notes_ref_shape.sql`. It keeps the same rule (1–512 printable ASCII characters, no space),
     spelled as an unbounded class plus `length() BETWEEN 1 AND 512`. 0001 is not edited: an applied migration is immutable.
   - **Test:** a schema test now also stores valid values at every bound.
2. **`ensureProduct` / `ensureComponent` under concurrency.** Both read the row back in the *same statement* as
   `INSERT … ON CONFLICT DO NOTHING`. When a concurrent transaction inserts the same key, the insert waits and returns nothing, and the
   same-statement read uses the statement's older snapshot, so the result was empty (`undefined` / `not_found`). This only happens on
   the first registration of a product or component, which is exactly CI's first run.
   - **Fix:** the read is a new statement.
   - **Tests:** a direct store test and the HTTP race test.

## 5. Audit and outbox

| Action | Category | Actor | Organization | Resource | Changes |
|---|---|---|---|---|---|
| `release.registered` | administrative | `{type: service, id: <caller>}` | `null` (platform-level) | `release` / its id | `product_id`, `component_id` (UUIDs), `kind` (closed set) |
| `release.published` | administrative | same | `null` | same | same |

**Catalog.** Additive (A50; ADR-0051 §9 named both actions): `release-service` is added to `CORE_PRODUCERS`, and the catalog document is
regenerated. As for every new action, **audit-service must be deployed with this catalog before release-service emits**.

**Platform-level.** No Organization is invented, Product is not used as Organization, and Company is not involved.

**Bounded evidence:**
- no version text: the catalog has no free-text change type, and the record names the release by id, with release-service as the
  authority for what it is;
- no build id, source revision, notes reference or product key;
- no token, header, request body, database URL or stack trace.

This is tested on the outbox payload and again on the stored `audit_record`.

**Truthful evidence.** Evidence is written **only when the row changed**:
- an idempotent retry writes nothing, so the trail never claims a second registration or publication;
- belt and braces: the event id is a version-5 UUID of `(release id, action)`, so even a second write of the same fact would be ignored by
  the outbox (and by audit-service's `(source, event id)` uniqueness).

**Atomicity.** The kit `AuditEventWriter` refuses a non-transaction client (`transaction_required`) and writes into the outbox **on the
mutation's own transaction**. If the intent cannot be written, the whole mutation rolls back: no release, component or product row, and
the status stays `registered`. The CI retry then succeeds and writes once. Audit-service is never called synchronously.

**Broker or audit outage after commit.** The mutation is committed and answered (201 / 200). The intent waits in the outbox (the relay
retries with backoff, logging `outbox_publish_failure`), and it is delivered, exactly as recorded, when the broker returns. This is tested
in-process with a switchable bus, and cross-service with audit-service stopped and restarted: one record.

**Correlation.** The request's (bounded) correlation id is stored on the outbox row and the audit record. It is never authority.

**Events.** release-service produces only this audit intent. It consumes nothing, and notifies, bills and deploys nothing.

## 7. CI/CD and other boundaries

**CI/CD.** CI builds, tests, packages and deploys or distributes, then tells release-service two facts: "this release exists" and "this
release is now published". release-service does not:
- build, test or deploy;
- upload to a CDN, App Store or Play Store;
- drive an updater;
- roll back;
- sign.

Registration is target-neutral across the five kinds: no Tauri, store or web-deployment behaviour.

**Other services.** It calls none: not Billing, Subscription, Entitlement, Payment, File, Notification or Auth. Authority is not a
commercial entitlement.

**Data plane.** No product request path depends on it: it is control-plane automation.
